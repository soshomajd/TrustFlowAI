## Architecture and decisions to preserve

- PostgreSQL/backend state is off-chain workflow and indexing data; contract state is the source of truth for funds. Reconciliation must be idempotent and verify chain ID, receipts, bytecode/contract address, immutable participants/token, and ordered amounts before advancing backend status.
- Backend `decimal(18,2)` and frontend JavaScript `number` values are display/business units. Never pass them directly on-chain: define a decimal-string-to-`bigint` base-unit boundary and reject inexact conversion. MockUSDC uses 6 base-unit decimals.
- `PendingDeployment` and the transient `Deploying` (held only during an in-flight deployment attempt, via an atomic DB claim) exist only in the backend because no on-chain escrow exists yet at that point. On-chain lifecycle is `AwaitingFunding -> Funded -> Completed` or `Cancelled`; `workStarted` is a separate flag.
- Users sign fund/release/cancel/start transactions from their own wallets. The backend may prepare deployment data, read RPC state/events, and reconcile records, but must not hold user keys or make final financial decisions.
- No dispute/arbitration logic belongs in the current MVP. Milestones remain ordered and releasable once, one contract remains bound to one project, and cancellation remains pre-work only.

## Known issues and integration gap
- 2026-10-11 first full browser walkthrough (Playwright MCP, local Hardhat): registered a client and a freelancer, created a 3000 project split 1000/1200/800, applied for two of the three stages, accepted, created and deployed the escrow, funded it, started work on-chain, delivered with a file, had changes requested, resubmitted, and released both milestones. MetaMask cannot be driven from here, so `window.ethereum` was replaced by a test EIP-1193 provider that forwards every call, signing included, to the Hardhat node, which holds its own accounts' keys. This is the first time funding, start-work and release have been exercised at all.

- 2026-10-11 thirteen defects found and fixed by that walkthrough. Three were blocking: the client could not accept any partial proposal, because the UI compared the agreed price against the whole project budget, which a proposal covering some stages is never meant to equal (it now compares against the total of the stages that proposal claims, and `ProposalResponse`/`ProposalForClientResponse`/`MyProposalResponse` carry those stages so both sides can see them); approving a milestone looked its escrow up by project alone, so on a split project the released amount could be credited to another freelancer's escrow; and completion was decided from every milestone in the project, so one stage nobody had taken left a fully paid escrow stuck on `Funded` and the project never finished - escrow completion is now per freelancer while project completion still needs every stage, covered by `ApprovingAFreelancersLastStage_CompletesTheirEscrow_ButNotAPartlyStaffedProject`.
