# چک‌لیست انتشار TrustFlowAI

**وضعیت فعلی: نسخهٔ کاندید اعتبارسنجی محلی شده و قدم بعد آماده‌سازی staging خصوصی روی Sepolia است. انتشار با پول واقعی هنوز تأیید نشده.**

آخرین شواهد پرداخت با کیف پول واقعی روی شبکهٔ محلی از پروژهٔ آزمایشی کافه است. اعتبارسنجی نسخهٔ کاندید با PostgreSQL جدا و شبکهٔ شبیه‌سازی‌شده انجام شد. آزمون محیط میزبانی در مرحلهٔ staging ثبت می‌شود.

## ۱. نسخهٔ کاندید

- [x] تغییرات V3، رقابت پروپوزال، قفل فایل، مایگریشن‌ها و راهنماهای هر دو نقش در نسخهٔ کاندید جمع شدند.
- [x] ۳۸ خروجی محلی Ignition از فهرست Git خارج و برای کامیت‌های بعدی نادیده گرفته شدند. فایل‌های محلی باقی ماندند. اسکن الگوهای رایج کلید و نام فایل حساس در بسته و سابقهٔ مرتبط مورد تأییدشده‌ای پیدا نکرد. ABI و بایت‌کد V3 مورد استفادهٔ API با خروجی ساخت Solidity یکسان‌اند.
- [x] بیلد Release بک‌اند و Production سایت، TypeScript و ESLint پاس شدند. تست‌ها: ۴۳۰ از ۴۳۰ بک‌اند روی PostgreSQL تازه، ۲۳۷ از ۲۳۷ سایت و ۵۹ از ۵۹ قرارداد. بیلد سایت هنوز هشدار lockfile والد را می‌دهد و کامل می‌شود.
- [x] روی PostgreSQL 17 نصب تازه هر ۳۴ مایگریشن و ارتقا از مایگریشن قبلی با پروژه، پیشنهاد و پرداخت نمونه تأیید شدند. اجرای دوبارهٔ SQL ارتقا تغییری نداد و EF اختلاف مدل ثبت نکرد. پرداخت و کارمزد قدیمی حفظ شدند.
- [x] Next.js به ۱۶٫۴٫۵ و Pkcs به ۱۰٫۰٫۱۳ به‌روز شدند. گزارش نهایی npm برای بسته‌های اجرایی سایت و بلاکچین و گزارش NuGet مورد آسیب‌پذیری گزارش نکردند. [انتشار Next.js](https://github.com/vercel/next.js/releases/tag/v16.4.5) · [گزارش امنیتی Pkcs](https://github.com/advisories/GHSA-846f-f764-76mx)
- [ ] در آماده‌سازی staging، مالک هر سرویس و محل نگهداری پشتیبان و نسخهٔ بازگشت را مشخص کنیم. پیش از مایگریشن از پایگاه هدف پشتیبان بگیریم و بازیابی را روی کپی تمرین کنیم. در صورت خطا، ابتدا پذیرش و تأمین وجه جدید را متوقف کنیم، سپس سازگاری نسخهٔ قبلی با schema و تراکنش‌های ثبت‌شده را بررسی کنیم. بعد از شروع کار V3 از مایگریشن معکوس حذف‌کنندهٔ سابقه استفاده نکنیم.

**پیش‌نیاز ساخت:** .NET SDK 10، Node.js 24، npm، PostgreSQL 17 برای بازتولید تست و کامپایلر تعریف‌شدهٔ Hardhat. دستورها در [راهنمای مخزن](../AGENTS.md) هستند. برای استقرار، بیلد سایت با URL و پیکربندی صریح محیط مقصد دوباره ساخته می‌شود.

## ۲. Staging خصوصی بسازیم

- [ ] دامنه، میزبان فرانت‌اند Next.js و API .NET، PostgreSQL جدا، سرویس SMTP با TLS معتبر و ClamAV را مشخص کنیم. staging حساب، فایل، اسرار و دیتابیس جدا داشته باشد.
- [ ] سایت و API را با URL صریح HTTPS و پیکربندی مشخص Sepolia بالا بیاوریم. شناسهٔ شبکه، RPC، آدرس و دقت توکن، کیف پول deployer، داور و گیرندهٔ کارمزد با پیکربندی API و سایت تطبیق داده شوند. deployer فقط هزینهٔ استقرار را می‌دهد. امضای مالی با کیف پول طرفین یا داور انسانی انجام می‌شود.
- [ ] مسیرهای محلی ادمین را غیرفعال نگه داریم و فقط مسیر خصوصی ادمین را برقرار کنیم. دسترسی از اینترنت به صفحات و APIهای ادمین، احراز هویت ادمین و Review را با URL مستقیم امتحان کنیم. API فعلی درخواست مدیریت دارای هدر Forwarded یا X-Forwarded-For را رد می‌کند و peer مستقیم را بررسی می‌کند. مسیر پراکسی خصوصی را با همین رفتار طراحی و از دورزدن origin جلوگیری کنیم.
- [ ] CORS، HTTPS، refresh cookie و نشست را روی دامنه‌های نهایی staging بررسی کنیم. کلیدهای لازم ASP.NET Data Protection، اسرار، دسترسی پایگاه داده و رفتار پس از restart یا تعویض replica مشخص باشند.
- [ ] راهنمای Sepolia را به جریان V3 و استقرار میزبانی‌شده به‌روز کنیم. دستورهای مربوط به V2 و تأمین کل بودجه در راهنمای فعلی تاریخی‌اند. [راهنمای Sepolia در مخزن](SEPOLIA_TESTNET.md)

**خروجی مرحله:** آدرس‌های staging و محیط آمادهٔ ثبت‌نام با ایمیل واقعی و توکن آزمایشی. [راهنمای شبکه‌های Ethereum](https://ethereum.org/developers/docs/networks/) · [استقرار Next.js](https://nextjs.org/docs/app/guides/self-hosting) · [پراکسی ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0)

## ۳. از ثبت‌نام تا پایان پروژه را روی staging قبول کنیم

- [ ] **حساب‌ها:** یک کارفرما و دو فریلنسر با ایمیل و مرورگر جدا از صفحهٔ عمومی ثبت‌نام کنند. ایمیل تأیید و ارسال مجدد، ورود، خروج، تمدید نشست بعد از رفرش، بازیابی رمز و خطاهای قابل فهم بررسی شوند. هر نقش فقط به صفحه‌ها و داده‌های خودش دسترسی داشته باشد.
- [ ] **کیف پول:** هر نقش آدرس جدا را با امضای مالکیت تأیید کند. تغییر حساب، شبکهٔ اشتباه، کمبود توکن یا گس و رد امضا مسیر بازیابی روشن داشته باشند.
- [ ] **استخدام:** کارفرما بدون پرداخت پروژه و مایلستون بسازد. دو فریلنسر برای یک مایلستون پیشنهاد بدهند. لغو یا شکست پرداخت، رقیب را رد نکند. واریز تأییدشده دقیقاً مبلغ همان مرحله را قفل کند، رقیب همان مرحله را رد کند و شروع فقط با امضای فریلنسر منتخب ممکن باشد.
- [ ] **تحویل:** فریلنسر نسخهٔ اول را ارسال کند، کارفرما اصلاح بخواهد و نسخهٔ دوم ثبت شود. قبل از پرداخت کامل، پیش‌نمایش محدود قابل مشاهده و اصل فایل و لینک سورس بسته باشند. دانلود مستقیم کارفرما و کاربر ثالث قبل از مجوز رد شود. اختلال اسکنر باید آپلود را متوقف کند.
- [ ] **تسویهٔ عادی و مراحل بعدی:** پس از تأیید، رسید و موجودی قرارداد با مبلغ ناخالص، ۱۰٪ کارمزد و دریافتی خالص تطبیق کنند و دانلود همان مرحله باز شود. مرحلهٔ بعدی همان فریلنسر در همان قرارداد تأمین شود. مرحلهٔ فریلنسر دوم قرارداد جدا داشته باشد. آخرین مرحله و بسته‌شدن پروژه در هر دو داشبورد بررسی شود.
- [ ] **خطا و بازیابی مالی:** برگشت تراکنش، کلیک دوباره، قطع RPC/API پس از موفقیت تراکنش، رفرش و restart را امتحان کنیم. همگام‌سازی باید همان تراکنش را بازیابی کند. رسید، پرداخت یا قرارداد تکراری ایجاد نشود.
- [ ] **داوری:** لغو پیش از شروع، بازپرداخت، پرداخت جزئی، اعلان و کد پیگیری دو طرف و عدم باز شدن فایل بعد از پرداخت جزئی را تأیید کنیم. داور مجاز فقط پس از مهلت می‌تواند رأی مالی را امضا کند. روی Sepolia مهلت واقعی را رعایت کنیم. مرزهای زمانی و مسیر ۹۰روزه را روی شبکهٔ کنترل‌شدهٔ همان کد با شواهد مستقل بررسی کنیم.
- [ ] **استفادهٔ واقعی:** مسیر بالا روی دسکتاپ و موبایل و با کیف پول‌های پشتیبانی‌شده از ورودی عمومی بررسی شود. راهنماهای هر نقش با متن و رفتار نسخهٔ منتشرشده هم‌خوان باشند.

**خروجی مرحله:** برای هر سناریو تاریخ، نسخه، نقش، نتیجه و برای مسیر مالی شناسهٔ رسید و اختلاف احتمالی حسابداری ثبت شود.

## ۴. قبل از باز کردن پول واقعی

- [ ] **قرارداد و زنجیره:** بازبینی مستقل قرارداد نهایی V3 و bytecode مورد استفادهٔ API. رفتار فعلی انصراف و بازکردن دوبارهٔ پرونده، مهلت را از نو حساب می‌کند. اثر آن بر خروج از اختلاف و امکان معطل ماندن وجه باید قبل از انتشار تعیین تکلیف و آزموده شود. شبکهٔ نهایی، سازگاری نسخهٔ کامپایلر و EVM، توکن واقعی، دقت، آدرس‌ها و کارمزد تأیید شوند. `testnet: true` ثابت، پیش‌فرض‌های محلی، mint آزمایشی و متن‌ها با محیط انتشار هم‌خوان شوند. [ملاحظات امنیتی Solidity](https://docs.soliditylang.org/en/latest/security-considerations.html)
- [ ] **همگام‌سازی روی شبکهٔ واقعی:** سیاست تأیید بلاک و برخورد با بازسازمان‌دهی زنجیره را ثبت و آزمون کنیم. خواندن تاریخچهٔ اجرا از بلوک استقرار تا آخرین بلوک در کد فعلی تکرار می‌شود. زمان، هزینه و محدودیت RPC برای قراردادهای قدیمی‌تر را بسنجیم و مسیر بازیابی و هشدار برای ناهماهنگی تعریف کنیم.
- [ ] **امنیت و عملیات:** ورود ادمین با کد واقعی، انقضای نشست، جداسازی مدیریت، محافظت از فایل‌ها و عدم cache عمومی دادهٔ خصوصی تأیید شوند. پشتیبان PostgreSQL با دادهٔ فایل‌ها واقعاً بازیابی شود. هشدار برای خطای ثبت‌نام/ایمیل، API، اسکن، RPC و رسید همگام‌نشده برقرار باشد. برنامهٔ توقف پذیرش یا واریز جدید و دسترسی به پرونده‌های باز در زمان اختلال آماده و تمرین شود. قراردادهای قبلی با rollback سایت برنمی‌گردند.
- [ ] **آمادگی محصول:** شرایط استفاده، حریم خصوصی، کشورهای هدف، کارمزد و شرایط بازپرداخت و اختلاف را برای بازار انتخابی بررسی و منتشر کنیم. کانال پشتیبانی، گزارش تخلف و مسئول رسیدگی از روز اول مشخص باشد. برای بتای محدود می‌شود از مسیر دستی مشخص استفاده کرد. صف داخلی گزارش و مجوزهای جزئی کارکنان را جدا برای عرضهٔ گسترده زمان‌بندی کنیم.
- [ ] **تصمیم انتشار:** اول نسخهٔ دعوتی با سقف پروژه و مبلغ مصوب، پایش خطا و بازبینی روزانهٔ مانده و رسیدها. انتشار عمومی پس از قبولی چک‌لیست و خروج موفق از بتا.

## اولین اقدام اجرایی

مقصد staging و مالک ایمیل/زیرساخت را تعیین کنیم. پس از استقرار خصوصی، کارفرما و فریلنسر با حساب و کیف پول تازه روی نسخهٔ میزبانی‌شده از ثبت‌نام شروع می‌کنند.
